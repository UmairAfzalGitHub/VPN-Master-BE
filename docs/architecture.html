VPN Master Architecture

Three independent pieces — the iOS app, the control plane on Render, and a WireGuard node on a DigitalOcean droplet. The one rule that explains everything: your traffic runs phone ⇆ droplet and never passes through Render. Render only coordinates.

Data path — your encrypted traffic (the actual VPN)
Control path — thin HTTPS setup & metering calls

How a connection happens

The exact sequence, verified end to end — from tapping Connect to packets flowing.

STEP 1

Generate keys

The app makes a fresh WireGuard keypair. The private key never leaves the phone — only the public key is sent.

STEP 2

Negotiate a session

POST /v1/sessions with serverID + publicKey. The control plane checks quota and premium.

STEP 3

Allocate & program

Postgres allocates a tunnel IP 10.8.0.x; the API tells the node agent to add the peer (with a PSK).

STEP 4

Agent runs wg

On the droplet the agent runs wg set wg0 peer … — the only place a WireGuard command ever executes.

STEP 5

Build the tunnel

The app assembles the config from the response and calls startVPNTunnel() in the extension.

STEP 6

Handshake → connected

A Noise handshake completes to 192.34.58.185:51820. Traffic now flows phone ⇆ droplet ⇆ internet.

Metering, without being in the way

Postgres is the ledger; the node is where traffic happens. They reconcile by polling — the API is never in the packet path.

EVERY ~60s

Poll the node

The poller calls the agent's GET /metrics, which reads wg show wg0 dump — per-peer RX, TX, last handshake.

ACCUMULATE

Add the delta

It stores each reading and adds only the difference to the device's monthly counter — reset-tolerant, summed across nodes.

SURFACE

Report to the app

GET /v1/usage returns usedBytes / remainingBytes against the 1 GB free monthly cap.
