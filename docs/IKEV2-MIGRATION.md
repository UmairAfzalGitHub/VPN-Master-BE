# IKEv2/IPsec Migration Plan

**Goal:** Replace the WireGuard data plane with **native IKEv2/IPsec** on both
clients, so neither app ships a third-party tunnel:

- **iOS** uses the built-in `NEVPNProtocolIKEv2` on `NEVPNManager` — no
  packet-tunnel extension, no `WireGuardKit`/wireguard-go.
- **Android** uses the platform `VpnManager` + `Ikev2VpnProfile` (API 30+;
  current `minSdk = 31`, so no floor change) — no `GoBackend`.
- **Nodes** run **strongSwan** instead of `wg` + `nftables` peer programming.

This touches all three repos: `VPN-Master-BE` (control plane + node agent),
`PeakVPN` (iOS), `PeakVPN-Android`. Each gets its own `feat/ikev2` branch.

> **Status: DONE (2026-11-21) — kept as a historical decision record.** The migration was
> carried out and WireGuard has been removed everywhere (backend migration 014, both apps).
> The sections below are the *original plan*; for how things work now read

## 1. Why this is a rewrite, not a swap

The current stack is WireGuard-specific at every layer. IKEv2 has a different
identity and auth model (negotiated SA + EAP/cert, not static keypairs), so each
layer is **replaced**:

| Layer | Today (WireGuard) | After (IKEv2) |
|---|---|---|
| iOS tunnel | `NEPacketTunnelProvider` + `WireGuardKit` | `NEVPNProtocolIKEv2` on `NEVPNManager` (no extension) |
| Android tunnel | `GoBackend` in-process `VpnService` | `VpnManager.provisionVpnProfile(Ikev2VpnProfile)` |
| Client identity | client WireGuard pubkey | EAP identity (per-device username/password) + server cert |
| Session negotiate | `POST /v1/sessions` registers pubkey, allocates tunnel IP, returns peer config | `POST /v1/sessions` issues short-lived EAP credentials + server coordinates |
| Node data plane | `wg set` peers + per-pubkey `nftables` quota | strongSwan `swanctl` connections/pools + per-IP accounting |
| Metering | `wg show` rx/tx per pubkey | RADIUS accounting or `ip -s xfrm` per session |
| Connect gating | custom extension redeems a connect-grant at `/authorize` | short-lived credentials (no extension to run code at connect) |

**The two hard parts are quota enforcement/metering and the connect-gate**, both
of which lean on WireGuard-specific mechanisms today. Everything else is
mechanical.

## 2. Auth model decision

strongSwan authenticates the **server by certificate** (the client validates it)
and the **client by EAP**. For an anonymous, no-login, per-device app the two
realistic options:

| Option | Client auth | Pros | Cons |
|---|---|---|---|
| **A. EAP-MSCHAPv2** (recommended) | per-device username + password generated by BE | simplest on both OSes; trivial to rotate; maps cleanly to `NEVPNProtocolIKEv2` and `Ikev2VpnProfile` username/password builders | password-based (mitigated by short TTL + TLS-protected EAP) |
| B. EAP-TLS / client cert | per-device client certificate issued by BE | strongest; no shared secret on the wire | BE must run a CA, issue/revoke certs; cert install UX on both platforms is heavier |

**Recommendation: EAP-MSCHAPv2 with short-lived, per-device credentials.** The BE
generates a `(username, password)` pair when the app asks to connect; strongSwan
(via a RADIUS backend, see §4) accepts it only while valid. This also *becomes*
the connect-gate (§6) — stale creds from a Settings-initiated reconnect are
rejected.

Server side needs a **publicly trusted or pinned server certificate** per node
(or a shared wildcard). Clients pin/validate `remoteIdentifier` = the node's cert
SAN. Plan for a cert per node issued from one internal CA, with the CA cert
bundled in both apps for validation.

## 3. Node design (strongSwan)

Replace the WireGuard node + `node-agent` with a strongSwan node:

- **strongSwan** (`charon-systemd` / `swanctl`) terminating IKEv2/IPsec.
- **Virtual IP pool** per node (reuse the existing `tunnel_subnet` per server, now
  handed to strongSwan's `pools`), so the DB's per-node subnet scheme carries over.
- **EAP via RADIUS** (`eap-radius` plugin → **FreeRADIUS**, local or co-located).
  RADIUS is what lets the BE inject per-device credentials dynamically and collect
  **accounting** (bytes in/out) for the quota ledger — it is the natural
  replacement for `wg show` metering.
- **NAT/forwarding** via `nftables` masquerade (the node already does NAT; only the
  per-peer quota table goes away).
- A **node agent** still exists but its contract changes (§5.3): it provisions
  RADIUS credentials and reports accounting, instead of `wg`/`nft` peer ops.

Firewall: keep UDP **500** and **4500** open (IKE + NAT-T), drop WireGuard's
51820.

---

## 4. Quota enforcement & metering — the biggest risk

Today the kernel drops a peer the instant it crosses its byte budget (per-pubkey
`nftables` quota), and `wg show` gives cheap rx/tx. IKEv2 has neither for free.
Options, in order of preference:

1. **RADIUS accounting + session-level enforcement (recommended).**
   FreeRADIUS receives Accounting-Start/Interim/Stop from strongSwan with
   `Acct-Input/Output-Octets`. The BE polls/receives these into `usage_counters`
   (reusing the existing ledger). To enforce, the BE sends a **RADIUS
   Disconnect-Message (CoA)** to drop a session that exceeds quota, and refuses to
   issue fresh credentials once exhausted. Enforcement latency = Interim-Update
   interval (e.g. 60s), vs. instantaneous today — acceptable for a data cap.

2. **Per-virtual-IP `nftables` quota.** Since each session gets a virtual IP from
   the pool, arm an `nftables` byte quota keyed on that IP (closer to today's
   model). Requires the agent to map IP↔device and sweep expired sessions. More
   code, but keeps near-instant enforcement.

3. Hybrid: nftables for the hard cutoff, RADIUS accounting for the ledger.

**Decision needed** (see Open Questions). Start with option 1; it reuses the
ledger and is least node-side code.

## 5. Backend changes (`VPN-Master-BE`)

### 5.1 Schema (new migrations)

- `011_protocol_column.sql` — `ALTER TABLE servers ADD COLUMN protocol TEXT NOT
  NULL DEFAULT 'wireguard'` (`'wireguard' | 'ikev2'`). Lets both coexist and roll
  out per-server.
- `012_ikev2_sessions.sql` — new `ikev2_sessions` table replacing the pubkey
  `peers` model for IKEv2 servers: `device_id`, `server_id`, `eap_username`,
  `eap_password_hash`, `assigned_ip` (nullable until strongSwan assigns),
  `expires_at`, `revoked`, timestamps. Keep `peers` untouched for WireGuard nodes.
- `servers` gains IKEv2 coordinates: `ike_remote_id` (cert SAN), and reuse
  `endpoint` (host, no `:51820`), `tunnel_subnet` (→ strongSwan pool), `dns`.

### 5.2 `/v1/sessions` redesign (protocol-aware)

`POST /v1/sessions` branches on `server.protocol`:
- **wireguard** → unchanged (existing pubkey/peer/grant flow stays live).
- **ikev2** → quota + premium gates as today, then:
  1. generate a short-lived `(eap_username, eap_password)`;
  2. provision them to the node's RADIUS (via the agent, §5.3);
  3. return `{ protocol: "ikev2", server: { host, remoteID, caCert | pinnedCert },
     eap: { username, password }, dns, expiresAt, quota }`.

`POST /v1/sessions/close` → revoke the credential + RADIUS CoA disconnect.
`/authorize` + the connect-grant columns are **not used** for IKEv2 (gating moves
to credential TTL, §6); keep them for WireGuard servers.

### 5.3 Node agent contract (new `ikev2-agent`)

Replaces the `wg`/`nft` agent for IKEv2 nodes. Same `X-Agent-Secret` auth. New
endpoints (driven by `services/provisioner`):
- `POST /credentials` `{ username, password, remainingBytes?, expiresAt }` → write
  to FreeRADIUS (and arm per-IP quota if using §4 option 2).
- `DELETE /credentials` `{ username }` → remove + CoA disconnect.
- `GET /accounting` → `[{ username, rxBytes, txBytes, lastSeen }]` for the ledger.

`services/provisioner` gains an IKEv2 implementation selected by
`server.provisioner`/`protocol`; `services/usagePoller` reads `/accounting`
instead of `/metrics` for IKEv2 nodes.

### 5.4 Untouched

Device identity (`/v1/devices`), premium/IAP gating, quota math
(`services/quota`), config endpoint, CORS/API-key gate — all protocol-agnostic
and stay as-is.

## 6. Connect-gate without an extension

Today, connecting requires the app because the packet-tunnel **extension** redeems
a single-use grant at `/authorize` before the handshake; a Settings-initiated
start carries no options and is refused. **Native IKEv2 has no extension process
to run that code.** Replacement:

- **Credentials are short-lived and issued only when the app asks to connect**
  (e.g. 2-minute TTL, mirroring `CONNECT_GRANT_TTL_SECONDS`). The app installs the
  IKEv2 profile with fresh creds, connects immediately, then they expire.
- A reconnect from iOS Settings / Android system UI reuses the **stale stored
  credential**, which RADIUS rejects → connection fails outside the app.
- Optional hardening: on connect the app first calls `/v1/sessions` to mint creds
  and only then writes them into the profile, so the profile never holds a
  long-lived secret.

This is arguably cleaner than the grant/arm dance and removes the `/authorize`
round-trip. Confirm the UX tradeoff: the OS may offer "reconnect" that now fails
with an auth error until the app is reopened (acceptable, and the intended gate).

## 7. iOS changes (`PeakPVN`)

Remove:
- The **PacketTunnel extension target** and its `WireGuardKit` dependency;
  `ThirdParty/wireguard-apple`.
- `WireGuardConfiguration`, the provider's `wg-quick` rendering, the grant-redeem
  code in `PacketTunnelProvider`.

Replace `TunnelManager` to drive **`NEVPNManager`** (not `NETunnelProviderManager`):
- Build `NEVPNProtocolIKEv2`: `serverAddress` = node host, `remoteIdentifier` =
  cert SAN, `localIdentifier` = eap username, `authenticationMethod = .none`,
  `useExtendedAuthentication = true`, `username` + keychain-ref `passwordReference`,
  `serverCertificateIssuerCommonName`/cert pinning via the bundled CA.
- `saveToPreferences` / `startVPNTunnel` / `stopVPNTunnel`, observe
  `NEVPNStatusDidChange` (status plumbing is nearly identical to today).
- Fetch EAP creds from `/v1/sessions` right before `startVPNTunnel` (§6), store the
  password in the keychain and pass `passwordReference`.

Net: **less** iOS code than today. `NetworkService`/`APIConfiguration`/models stay.

## 8. Android changes (`PeakVPN-Android`)

Remove the `wireguard.tunnel` (`GoBackend`) dependency, `WireGuardConfiguration`,
`WireGuardKeyPair`, and the raw-`VpnService` tunnel wiring.

Replace `TunnelManager` to use **`VpnManager`** (`Context.getSystemService`):
- Build `Ikev2VpnProfile.Builder(serverAddr, remoteId)` with
  `.setAuthUsernamePassword(username, password, serverRootCa)`, DNS, MTU,
  allowed/excluded apps as needed.
- `vpnManager.provisionVpnProfile(profile)` (fires the system consent intent,
  like today's WG prepare), then `vpnManager.startProvisionedVpnProfileSession()`.
- Status: platform IKEv2 doesn't expose a `Tunnel.State` flow like `GoBackend`;
  observe via the `VpnService`-level network callbacks / `ConnectivityManager`
  `NetworkCallback` on the VPN transport. **Verify the status-granularity we can
  get** (see Open Questions).
- `minSdk = 31` already satisfies the API 30 requirement — no manifest/floor
  change.

Note: platform IKEv2 gives less routing control than a raw `VpnService`; confirm
split-tunnel / per-app needs are still met.

## 9. Rollout strategy

Protocol coexistence via the `servers.protocol` column means **no flag-day cutover**:

1. Stand up **one strongSwan node** + FreeRADIUS alongside the WG fleet.
2. Ship BE changes (protocol-aware `/v1/sessions`, ikev2-agent, poller) — WG
   servers behave exactly as before.
3. Add one `protocol = 'ikev2'` server (e.g. a new region, or a dark/staging
   entry) and validate end-to-end with dev builds of both apps.
4. Ship app builds that handle both protocols (branch on `protocol` in the
   `/v1/sessions` response).
5. Migrate servers region-by-region by flipping `protocol` (+ swapping the node),
   watching the quota ledger and connect-gate behaviour.
6. Once all nodes are IKEv2, delete the WireGuard paths (peers table, wg-agent,
   WireGuardKit/GoBackend) in a cleanup pass.

## 10. Open questions (resolve before building)

1. **Quota enforcement model** — RADIUS CoA (option 1) vs per-IP nftables
   (option 2)? Affects node agent + latency guarantees.
2. **Server certificates** — one internal CA with per-node certs (bundle CA in
   apps), or publicly trusted certs? Revocation story.
3. **Android status granularity** — can we surface connecting/connected/reconnecting
   as richly as `GoBackend` does? Prototype first; it may change the UI's state
   model.
4. **Metering fidelity** — RADIUS interim interval vs. today's near-real-time
   `wg show`; acceptable for the data cap?
5. **Keep WireGuard as a fallback protocol** for networks that block IKEv2
   (UDP 500/4500 are commonly throttled), or full replacement? The `protocol`
   column supports keeping both if desired.
6. **IAP/premium, DNS, MTU** — confirm no behavioural regressions under IKEv2
   (e.g. MTU/MSS clamping differs from WG).
